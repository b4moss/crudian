## 共通前提

| 項目 | 値 |
|------|-----|
| 対象 | `@b4moss/crudian/bun-sqlite` / `drizzle` / `prisma`（JS 既存3系統） |
| 契約の正 | 共有層の語彙。参照実装の詳細確認は bun-sqlite。drizzle / prisma は同等観測 |
| 入口 | `createCrud(db)`（既存） |
| `count` 戻り値 | `number`（async アダプタは `Promise<number>`） |
| `count` 第2引数 | `CountQuery`（`{ where?: WhereInput }`）。`limit` / `cursor` / `columns` は受け取らない |
| `SearchResult` | `{ items, nextCursor, hasMore, total }`（本版で `total` を常時付与） |
| `total` の意味 | `where` に一致する全件数。`limit` / `cursor` の影響を受けない。ページの `items.length` ではない |
| `list` | 引き続き `search` の別名（`total` 込みで同一結果） |
| where コンパイル | `count` は既存 `search` と同じ where コンパイル経路を流用する（別方言を増やさない） |
| オプトイン | `total` 省略フラグは設けない（毎回 COUNT 相当を取る） |
| 識別子 / エラー | 既存どおり（文字列必須・形式検証なし。独自エラー最小。他は下位例外） |
| 対象外（本ファイル） | Turso（#42）、offset、orderBy、全文検索、演算子追加、Go / PHP |

フィクスチャ表（例）は整数主キー `id` を持つ単表。スキーマはテスト内 DDL で用意してよい。  
v0.1〜v0.3 の CRUD / 条件ビルダー / cursor ページング / extended writes は回帰として壊さない。  
**契約変更:** 旧仕様の `SearchResult`（`{ items, nextCursor, hasMore }`）は本版で `total` を必須フィールドとして追加する。

## bun-sqlite（参照実装）

パッケージ: `@b4moss/crudian/bun-sqlite`  
ランタイム / テスト: Bun + `bun:test`  
DB: 呼び出し側注入の `bun:sqlite` `Database`（テストでは `:memory:`）

### bun.count

- 条件に合う行の件数を数値だけで返す
- SQL イメージ: `SELECT COUNT(*) FROM table [WHERE ...]`
- `where` なしはテーブル全件数
- `where` ありは `search` と同じ条件集合の件数

#### テスト：正常系

- 空表で `count(table)` が `0` を返す
- 複数行を挿入したあと `count(table)` が行数と一致する
- `where` ありで一致件数だけを返す（例: 名前一致が2件なら `2`）
- 条件に0件のとき `0` を返す（throw しない）
- `eq` / `and` / `or` / 比較 / `in` / `like` / `isNull` / `isNotNull` で絞った件数が、同じ where の `search(...).items` を全件取得した長さと一致する（limit を十分大きくした場合）
- Facade に `count` が関数として存在する

#### テスト: 異常系

- テーブル名が文字列でないとき拒否する
- 存在しないテーブル参照は SQLite 例外になる
- `in` に空配列を渡したときの扱いが `search` と同じ（拒否または0件。一方に固定）
- カラム名が文字列でない when（where 経由）は `search` と同じ拒否になる

---

### bun.searchTotal

- `search` の戻りに `total` を常時含める
- `total` は `count(table, { where: query.where })` と同値（cursor / limit を無視した全件数）
- `items` / `nextCursor` / `hasMore` の計算は v0.1.0 どおり（`id` 昇順 cursor）

#### テスト：正常系

- 条件なしで全件 N 件のとき、任意の `limit` でも `total === N`
- ページ途中（例: N=5, `limit=2`）で `items.length === 2` かつ `total === 5`
- `cursor` を進めた2ページ目以降でも `total` は同じ N のまま（ページ位置で変わらない）
- `where` ありで一致 M 件のとき、ページングしても `total === M`
- `hasMore=false` の最終ページでも `total` は全一致件数のまま
- 0件のとき `items` は空、`hasMore=false`、`nextCursor=null`、`total === 0`
- 返却オブジェクトのキーに `items` / `nextCursor` / `hasMore` / `total` がある

#### テスト: 異常系

- `limit` 不正など既存の `search` 拒否はそのまま（`total` 追加で緩和しない）
- 存在しないテーブル参照は SQLite 例外になる

---

### bun.listTotal

- `list` は `search` の別名であり、`total` 込みで同一結果を返す

#### テスト：正常系

- 同じ引数で `list` と `search` の結果が deep equal（`total` 含む）
- cursor ページングでも両者の各ページが一致する

#### テスト: 異常系

- `search` と同じ入力で同じ拒否／例外になる

---

### bun.createCrudSurface

- 既存メソッドに加え `count` を公開する

#### テスト：正常系

- 返却オブジェクトに `count` がある（既存の CRUD / `search` / `list` / `transaction` / extended writes も維持）

#### テスト: 異常系

- （入口の拒否は v0.1.0 どおり。本版で変更しない）

## 回帰（スモーク）

### regressionAfterTotal

- v0.1〜v0.3 の振る舞いを壊さない（`SearchResult` に `total` が増えたこと以外）
- cursor / 条件ビルダー / upsert / bulk* / transaction が引き続き動く

#### テスト：正常系

- `create` → `read` が行を返す
- `search` の `items` / `hasMore` / `nextCursor` が従来どおり進む（加えて `total` がある）
- `list` と `search` が同結果
- `upsert` / `bulkCreate` など既存 extended のスモークが通る（触る範囲でよい）

#### テスト: 異常系

- `read` 未ヒットは引き続き `null`
- `update` 0件は引き続き `null`
- 不正 `limit` は引き続き拒否
